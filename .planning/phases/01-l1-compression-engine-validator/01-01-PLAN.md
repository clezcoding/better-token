<objective>
Walking Skeleton for Phase 1: prove the full stack end-to-end by letting a user run `better-token compress <rule-file.md> --dry-run` and see a real estimated token delta with a byte-exact validation gate that refuses to corrupt code blocks, inline code, URLs, paths, frontmatter, headings, or any of the SAFE-02 semantic carve-outs (exact error strings, commit/PR messages, security warnings, irreversible-action confirmations, multi-step sequences).

This is a vertical slice, not a layer cake: after Task 2 the user can already run a real dry-run; after Task 3 the dry-run shows a real delta and the validator catches corruption of syntax regions; after Task 4 the validator also catches corruption of semantic carve-outs, closing the full SAFE-02 list. Write/backup/rollback (Plan 02) and safe/aggressive modes + interactive prompts (Plan 03) build on this skeleton.

Note: This plan has 4 tasks (one over the 2-3 guideline) because SAFE-02's full carve-out list is a Phase 1 requirement that must be covered in the walking skeleton — splitting it into a separate plan would create wave/dependency conflicts with Plan 02 (which extends `compressor.ts` and `index.ts`) and Plan 03 (which extends `compressor.ts` and `cli.ts`). Each task stays within ~15% context, so the 4-task plan remains under the 50% context target.

Purpose: Establish the architectural backbone (monorepo, TS, regex protected-token pattern, bpe-lite estimation, byte-exact gate, SAFE-02 carve-out detection) that every later phase imports via `packages/core`. Without this slice, no later phase can compress anything safely.
Output: Working `compress --dry-run` command, real tokenizer + balanced-mode compressor + byte-exact validator + carve-out detector, unit + integration test scaffolding, SKELETON.md (already written).
</objective>

<assumptions>
- **A1 (from 01-RESEARCH.md `## Assumptions Log`):** `bpe-lite` token estimation is accurate enough for Phase 1 stats. Risk if wrong: low — token figures are explicitly labeled `estimated` (D-09) in CLI output, and exact measured metrics arrive in Phase 4 (STAT-02). No mitigation needed in Phase 1 beyond the `estimated` label.
- **Frontmatter handling (from 01-RESEARCH.md `## Open Questions (RESOLVED)`):** YAML frontmatter is a protected byte-exact token — `tokenizeMarkdown` splits it from the body first and protects it under a single `__FRONTMATTER_0__` placeholder; `detokenizeMarkdown` restores it verbatim; the validator asserts frontmatter byte-equality. Implemented in Task 3; tested in `tokenizer.test.ts` + `validator.test.ts`.
- **Regex vs remark (from 01-CONTEXT.md "Claude's Discretion"):** Planner chose the line-based regex protected-token pattern (ported from caveman-compress prior-art) over `unified`/`remark-parse`/`remark-stringify`. The protected-token regex isolates syntax regions as immutable placeholders before any prose compression, delivering the same 0%-substance-loss guarantee as AST parsing without the serialization drift risk of a remark round-trip. `unified`/`remark-parse`/`remark-stringify` are therefore NOT Phase 1 dependencies.
- **Carve-out heuristics (from 01-CONTEXT.md "Claude's Discretion"):** The exact regex patterns for the five SAFE-02 semantic carve-out categories (error strings, commit/PR messages, security warnings, irreversible-action confirmations, multi-step sequences) are conservative line-based heuristics. False positives (over-protection) are acceptable — they only reduce compression ratio, never corrupt content. False negatives are caught by the byte-exact validator when a heuristic mutates a line, and by the negative test in Task 4 that feeds carve-out lines through aggressive compression.
</assumptions>
